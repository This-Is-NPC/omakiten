## Architectural Patterns

- **Hexagonal / Ports and Adapters**: `internal/app/ports.go` declares every repository port; right-side adapters (`internal/sqlite`, `internal/configstore`) implement them; left-side adapters (`internal/cli`, `internal/tui`, `internal/mcp`, `internal/agentruntime`) are composition roots that construct app services and inject the right-side adapters. The diagram and rules are documented in `internal/app/doc.go`.
- **Boundary enforcement**: `internal/arch/arch_test.go` parses every non-test file under `internal/` and asserts that domain has no outward deps, app does not import concrete adapters, and `sqlite`/`configstore` do not import each other or app. The same rules are mirrored under `depguard` in `.golangci.yml`.
- **TUI screen-host boundary**: `internal/tui/screenhost` owns stable screen IDs, immutable `Frame` snapshots, semantic outcomes, lifecycle events, reload policies, and validated descriptors. The root `Model` remains the only owner of project/theme/catalog/status, global overlays, application services, refresh generation guards, and the navigation stack; factories receive the narrow `screenhost.Host`, never `*tui.Model`. `screen_registry.go` projects the existing top/sub cycle, labels, palette routes/codes, help availability, reload policy, and renderer dispatch from one descriptor list. `internal/arch/tui_screen_boundary_test.go` rejects imports of root `internal/tui` from `components`, `screenhost`, and `screens` packages, and ratchets the completed extractions: each extracted package must declare a `Screen` type and the root renderer it replaced must stay deleted.
- **TUI screen extraction shape**: an extracted screen is a value type implementing `screenhost.Screen` in its own package under `internal/tui/screens/`. It holds its own cursor, scroll offset, local modes and loaded projection, and receives immutable per-frame geometry/theme/text plus host-built payloads. Screens report intent through `screenhost.Outcome` and never call repositories or write root/task-detail state. Persona-skill and Template-default use one parameterized `relationshippicker.Screen`: it normalizes candidates, owns single/multi selection and dirty-discard confirmation, and stamps typed outcomes with the open generation. The host rejects those outcomes before storing screen state unless route, entity, and generation still match; it then validates candidate identities and executes `PersonaService` or `TemplateService`. `screenStack` dispatches enter/leave/resize and preserves the parent beneath pushed routes. Footers declare screen-owned ordering; the host appends global navigation bindings unless the screen implements `FooterOwner`. `internal/tui/screen_host.go` is the root half: `bind → fetch → store`, with parameterized families stored by stable screen ID.
- **Shared task projection**: `internal/taskprojection` is the one non-UI owner of task/dependency relation semantics shared by Board, Table and Task Detail. The host builds it from the live snapshot and passes it into each screen; the projection owns root/subtask and priority/bucket filtering, deterministic ordering, child grouping, blocker/parent lookup, counts and final-bucket completion classification. Screens may retain compatibility input scaffolds for isolated fixtures, but production binding receives the structured projection and does not re-traverse task relations.
- **TUI render toolkit**: `internal/tui/components/screenkit` owns the shared panel, rule, cursor-marker, summary-table, scroll-window and viewport-budget algorithms plus the pure text helpers (sanitize, truncate, indent, pad, clamp, page step). The root `Model` helpers (`renderPanel`, `hRule`, `cursorMarker`, `summaryRows`, `renderSummaryTables`, `renderScrollWindowSplit`, `sliceScrollRows`, `panelViewportRows`, `availableWidth`) delegate to a `Kit`, so root and every extracted screen share exactly one implementation. `styles.screenStyles()` is the single crossing point from the root theme into the screen-facing `screenkit.Styles` projection. Chrome height is host-only knowledge: the root measures it (`hostChromeRows`) and publishes it on the frame as `ChromeRows`, because the screen header and status badge render outside the screen boundary.
- **Registered task-form ownership**: `internal/tui/screens/taskform` is the registered Task create/edit route and owns Title / Description / Priority / Tags / Parent widget state, section focus, dirty-discard state, and resize calibration as screen form code. Line prompts and the description area paint through `internal/tui/components/field`. The screen owns mode, initial values, lookup loading/error presentation, footer/help, and emits typed save/cancel/lookup/blocker intents stamped with its generation. `internal/tui/screen_host.go` rejects stale route/generation/task outcomes before storing screen state, then alone performs project-aware lookup, anti-cycle validation, tag synchronization, service calls, and navigation. Architecture tests reject reintroduced root task inputs, focus/dirty state, create/edit modes, or render/update branches. Studio task #520 remains responsible for its separately specified YAML candidate/validation/save behavior.
- **Registered Task Detail ownership**: `internal/tui/screens/taskdetail` is the registered `tasks.detail` route. Its value model owns task/activity/subtask projection, focus and scroll, blocker multi-picker, comment composition, move selection, nested-task ancestry, resize and pending-result generation checks. It emits typed outcomes for comment, blocker, move, completion, deletion, form/reader navigation and refresh; `internal/tui/screen_host.go` alone invokes application services and rejects stale route/generation/task outcomes. Realtime activity workers fold through `taskdetail.Result`, preserving the focused event by stable ID.
- **Registered Description and Comment ownership**: `internal/tui/screens/description` (`tasks.description`) owns focused task-description scroll, markdown/plain mode, resize, loading/error projection, footer and help. `internal/tui/screens/commentdetail` (`comments.detail`) owns one explicit read/edit mode, textarea geometry, dirty/cancel behavior, comment scroll, markdown/plain mode, delete confirmation, loading/save-error presentation, footer and help. Both are pushed/popped through `screenStack`; the root has no open/edit booleans. Comment edit/delete permissions are resolved before open, and host-owned application services return `commentdetail.Result` so failed saves preserve the dirty buffer while successful saves return to read mode.
- **CQRS-like split**: Canonical YAML files are the write-model source of truth; SQLite is operational state only. The active schema contains no configuration tables; `app.ConfigService.Import` loads and hashes the bundle, while composition roots call `config.BuildSnapshot(bundle)` to materialise an immutable `*config.Snapshot` and emit `bundle.imported` for audit. Reads (workflow shape, personas, skills, laws, templates, notifications, mcp_commands, settings, synonyms, stopwords) go through the per-project snapshot captured at construction by app services. The SQL adapter touches `config.Bundle` / `config.Snapshot` in zero production files.
- **BundleCache + per-project ProjectRuntime (Phase 3)**: `agentruntime.BundleCache` keys a `*ProjectRuntime` per project id. Each `ProjectRuntime` aggregates one bundle's `*agent.Service`, `hooks.Engine`, `ActionRegistry`, `NotificationShowAction`, `EnumRegistry`, `NotificationSnapshot`, `TagSynonyms`, `Stopwords`, `SourcePath`, and `Mtime`. `BundleCache.Resolve(ctx, projectID, configPath)` returns a cached entry, rebuilds on mtime change, or builds the first entry on miss; `Reload` forces a serialized rebuild. Replacement engines are prepared inactive, consumer acceptance runs against staged state, and only then does commit apply Store settings, close old-engine admission at the same mutex-protected point used by dispatch, unsubscribe/cancel/drain admitted actions, start the replacement, and publish it. A rejected candidate leaves Store event rows byte-for-byte intact and remains retryable; a drain timeout is returned with the replacement unpublished, preventing old/new overlap and post-return old actions after successful reload. The same `BuildProjectRuntime` runs from every composition root (`agentruntime.Open`, `cli/root.go` open, `tui/reload_bundle.go` Reload) so boot and reload cannot drift. MCP `Adapter.CallTool` peeks `project` / `project_id` from incoming args and dispatches against the `ServiceResolver`'s reply; the static default is shielded behind `DefaultServiceProvider` so a cache rebuild does not leave the adapter holding a stale `*agent.Service` (`internal/agentruntime/cache.go`, `internal/agentruntime/runtime.go`, `internal/mcp/adapter.go`). Hooks engines filter dispatch by `engine.projectID` so two projects' bundles never cross-fire (`internal/hooks/engine.go matchesProject`); `hooks.GlobalProjectID` is an explicit zero-scope bootstrap/test contract, while normal runtimes use their non-zero project id. `bundle.imported` records that runtime id even though it uses `entity_type=system`; only intentionally global events use project 0 and reach every engine. Candidate acceptance/quarantine and retry preserve this attribution (`internal/agentruntime/cache.go`, `internal/hooks/engine.go`).
- **Current-path atomic file editing**: `app.BundleEditor` carries the caller's wiring and source-file hashes from a coherent `LoadPlan`/`LoadPlanWithFiles` capture into apply. The config adapter reads each source once, parses the captured bytes, and hashes those same bytes; apply never establishes a second planning baseline. A single process-wide mutex serializes source validation through wiring/entity publication and deletion, covering profile aliases, shared entity roots, runtime recreation, and platform-specific path aliases; planning reads and final reload run outside the critical section (`internal/app/bundle_editor.go`). It publishes operations independently with whole-file atomic writes and validated regular-file deletes. FileOps use relative paths below the current bundle root; absolute, parent-traversal, outside-root, and symlink escapes are rejected before publication. Linux and supported Unix/Windows backends validate no-follow paths and publish complete files; a later operation leaves already-published files intact, while post-publication durability errors are reported as ambiguous and final reload failures as published-but-unverified, both with reload/retry or repair guidance. This is an ordinary in-process concurrency precondition, not protection against cross-process same-user active replacement of regular files, which remains outside the boundary. Unsupported platforms fail closed for the safe-I/O operations.
- **SQLite transition**: the updater validates the exact v0.30.0 schema through a read-only SQLite connection before the normal bridge, while current databases use the ordinary Store lifecycle (`internal/sqlite/v030_eligibility.go`, `internal/sqlite/store.go`).
- **Workflow policy in app**: `app.WorkflowService` owns default-bucket resolution, transition allowance, guard evaluation, `task.completed` emission, and the per-bucket CRUD policy (`ResolveBucketPermissions`). The sqlite layer holds only persistence primitives (`internal/app/workflow_service.go`).
- **Data-driven CRUD policy**: per-bucket and workflow-level overrides for `task.{edit,delete}` / `comment.{edit,delete}` are declared in YAML and read from the in-memory `*config.Snapshot` (`Bucket.Permissions`, `Workflow.Defaults`). The resolver walks bucket → workflow defaults → implicit `true`; comment falls back to task at every layer. No hardcoded "first bucket is special" rule (`internal/domain/workflow.go:ResolveTaskPermission` / `ResolveCommentPermission`).
- **Configurable domain enums (id↔value tables)**: enums whose labels are user-facing (`config.priorities`, `config.severities`) are declared in YAML as `[{id, value, default?, color?}, …]`. Priority ids land in SQLite on `tasks.priority_id`; severities live on law frontmatter and are resolved at bundle import time. Code references the integer id only; renderers (TUI, CLI, MCP DTOs) resolve labels through an instance-scoped `*domain.EnumRegistry` returned by `app.ConfigService.Import` and injected via constructor into every service that needs it (`TaskService`, `LawService`, `WorkflowService`, `TUIQueryService`, agent `Service`). Domain types carry no `MarshalJSON` / `UnmarshalJSON` — wire format is the raw int id, and label projection happens at DTO boundaries (e.g. `agent.TaskSummary.Priority` is the resolved label string). Renaming a label is a YAML edit. Validator enforces ascending id order so the SQL sort weight and TUI cycle stay aligned with declaration order.
- **No canonical defaults in code**: the kit YAML at `defaults/config/omakase.yaml` (embedded via `go:embed`, materialised on first run by `internal/configstore.EnsureDefaultFiles`) is the **single canonical source** for every tunable. Code carries no `Default*` constants and no `Canonical*` slices for the configurable fields. The validator (`internal/config/validator.go`) treats every canonical field as required — bundles missing `mcp.*`, `tui.token_badge.*`, `views.*`, `priorities`, `severities`, `template_defaults`, `sqlite.{busy_timeout_ms,cache_size_kb,mmap_size_bytes}`, `solutions.*`, `backup.retention_count`, `events.{default_recent_limit,retention.*,defaults.*}`, `search.stopwords`, or `tag_synonyms` fail loud with messages pointing back at `defaults/config/omakase.yaml`. The `Effective*` accessors are identity passthroughs kept for explicit naming at call sites. A test-only helper (`internal/testfixtures.LoadBundle`) merges the embedded kit YAML on top of partial fixtures so test scenarios stay focused; production never falls back at runtime. Priority/severity resolution is fully dependency-injected via `*domain.EnumRegistry` (built from the validated bundle by `ConfigService.Import` and threaded through every service constructor — no process-global enum state remains). The two remaining process-global registries are tag synonyms in `internal/app` and stopwords in `internal/agent`: leaf helpers (`NormalizeTagName`, `wordSet`) have no per-call context to thread a resolver through. Composition roots (`agentruntime/runtime.go`, `cli/root.go`) are the single point that writes those two registries from the validated bundle. Connection-level SQLite knobs (`config.sqlite.*`, `config.events.{retention,default_recent_limit}`) flow into the live `sqlite.Store` via `Store.ApplyConfig` / `Store.SetEventsPolicy` after `ConfigService.Import`; service-level knobs (`config.solutions.{default_top_limit,max_top_limit}` and `config.mcp.*`) flow through the agent/app service settings.
- **Archive lifecycle**: tasks carry a `state` column (`active|archived`); `Archive`/`Unarchive` bypass bucket policy and transition guards but respect `operations.{archive,unarchive}.guards` (`internal/app/task_service.go`, `internal/sqlite/tasks_lifecycle.go`).
- **Sub-task hierarchy**: tasks may point at `tasks.parent_id`; app-layer checks and current-schema triggers keep parent/child rows in the same project, and `subtasks_complete` gates promotion while a direct child remains outside the workflow's final bucket (`internal/sqlite/tasks_parent.go`, `internal/app/guards/evaluator.go`).
- **Plan claim is ownership-only**: `Store.ClaimNextPlanTask` (and the `PlanService.ClaimNext` / MCP `plans.claim_next` / `okt plan claim` callers stacked on top of it) selects only active, unassigned tasks that are still in the workflow's first bucket, then writes `tasks.assigned_to` and emits `task.assigned` inside the `BEGIN IMMEDIATE` transaction — it never touches `tasks.bucket_id`. Bucket transitions on a claimed task still flow through `app.WorkflowService.MoveTask` so preset-defined transition guards stay authoritative (e.g. omakase's self-branch-comment requirement on `backlog → dev` is not bypassed by the claim path). Plan auto-finalisation (`plan.done`) is therefore triggered exclusively by the terminal-bucket move, not by claim (`internal/sqlite/plans.go`, `internal/app/plan_service.go`).
- **Coded errors**: Every domain error has a stable machine-readable code consumed by the JSON envelope and by the agent's recovery guidance (`internal/domain/errors.go`, `internal/agent/errors.go`).
- **Strict project scoping**: Operational rows are filtered by `project_id` at the repository layer (`internal/sqlite/tasks.go`, `internal/sqlite/comments.go`, `internal/sqlite/dependencies.go`, …).
- **Strict YAML validation**: `yaml.NewDecoder` uses `KnownFields(true)` to reject unknown fields and prevent silent drift (`internal/config/loader.go`, `internal/config/entity_loader.go`).
- **Protocol-neutral agent layer**: `internal/agent` knows nothing about MCP; `internal/mcp` is a thin translation layer; `internal/agentruntime` is the composition root.
- **Context-bound observability**: `activity.Track` uses context-scoped repositories so logging is opt-in per runtime and never breaks business logic (`internal/activity/track.go`, `internal/activity/context.go`).
- **Interactive notifications via CLI dispatch**: `config.Notification` cards accept an `Actions []NotificationAction` block (key/id/label/command). The notification component emits `ActionMsg{slug, action_id, command}` on a matching keystroke and the TUI Model runs `Command` in-process through `Repositories.DispatchCommand` (a closure built around `cli.NewRootCommand` so the same cobra root that serves the CLI also serves the prompt). The hooks engine pre-renders each `command[]` element through `text/template` against the triggering event's payload at NotificationShowMsg emit time so dispatch is dependency-free at key-press time. Every non-empty Command emits `confirmation.granted` keyed by ctx `author_type` (`human` from TUI, `agent` from any future MCP-driven surface) before the cobra invocation runs (`internal/config/notification.go`, `internal/tui/notification.go`, `internal/tui/notification_action.go`, `internal/hooks/actions/notification.go`). Validator blocks `tui` and `mcp` as the first command token — re-entering those surfaces from a hook deadlocks the live program.
- **Hot-reload of the active config bundle**: the TUI Settings → Config picker re-imports a chosen preset in place through `Model.reloadBundle` using BundleCache validation and commit. The candidate runtime, Store settings, and hook engine remain inactive while a copied Model validates and stages the new Snapshot, Workflow, EnumRegistry, editor, theme/styles, markdown/notifications, token-badge, and task snapshot; commit then publishes the Store/runtime and staged Model together. A rejected candidate leaves event rows and the prior runtime untouched, so the same source can be retried. `paths.SetActiveConfigInDir` writes the marker in `BundleEditor.ConfigDir` through descriptor-relative no-follow operations on supported Unix targets; targets without a native no-follow backend fail closed before marker I/O, preserving the prior marker and live state. A successful swap emits `bundle.swapped` with the orphan-preview payload; when orphans exist the model stashes the previous config path and the hook engine paints the `kitten_orphan_migration` prompt — esc on that prompt rebuilds against the previous bundle so the user is never left on a workflow they did not confirm (`internal/agentruntime/cache.go`, `internal/tui/reload_bundle.go`, `internal/tui/settings_picker.go`, `internal/paths/active_unix.go`).
- **Orphan-task migration on workflow swap**: tasks pointing at a bucket whose workflow is no longer active are *orphans*. `app.OrphanRepository` exposes `PreviewOrphanedTasks` (read-only) and `RebindOrphanedTasks` (in-tx). The rebind matches each orphan to the same key in the new active workflow (preserved) or to the first active bucket (removed) and emits `task.migrated` per task with payload `{from, to, reason: "workflow_swap"}`. The TUI dispatches it through the in-process cobra command `okt workflow orphans --confirm`; CLI and MCP surfaces (`orphans.migrate` tool, two-phase confirmation) reach the same primitive (`internal/sqlite/orphans.go`, `internal/app/orphan_service.go`, `internal/cli/workflow.go`, `internal/agent/service_orphan.go`).
- **Transactional event-emission lifecycle (W11-extension motif)**: `internal/sqlite/txevent.go`'s `TxMutation[T any]` + `txMutateAndEmit[T]` own the full `BeginTx → Mutate → Payload → insertEntityEvent/insertTaskEvent → Commit → publishEvent` cycle. `Mutate` runs inside the helper's transaction; `Payload` runs after `Mutate` but before the event INSERT so JSON-marshal failures roll the mutation back; `publishEvent` fires only post-commit by construction — subscribers can rely on "observed an event ⇒ row is on disk". `EventScope` discriminates between `insertEntityEvent` (plan / non-task entities) and `insertTaskEvent` (task feed) with one code path. Optional `ShouldLog func() bool` gate: when false, the helper skips the events-row INSERT but still publishes a synthetic envelope (mirrors the inline gated callsites — `CreateTask`, `MoveTask`, …). Migrated callers: `CreatePlan`, `UpdatePlanGoalBody`, `AddPlanWave`, `AssignTask`, `MaybeFinalizePlanForTask`, `CreateTask`. The scoped comment writers (`AddScopedComment` / `EditComment` / `DeleteComment`) hand-roll their own `BeginTx → mutate → emit → Commit → publish` cycle because they resolve the event's entity scope per comment (task / project / universal); they preserve the same post-commit-publish and gating invariants. `ClaimNextPlanTask` keeps its hand-rolled `*sql.Conn` + `BEGIN IMMEDIATE` shape (concurrency serialisation that `BeginTx (DEFERRED)` would lose, exercised by `TestClaimNextPlanTaskIsAtomicUnderConcurrency`) but publishes through the same post-commit gate (commit `5b25db6` closed a missing `publishEvent` on the success path that left the bus silent pre-fix). `MoveTask`, `SetTaskState`, `HardDeleteTask`, `RebindOrphanedTasks` remain inline pending a multi-event variant of `TxMutation` for primary + secondary event sequences.
- **Cursor/scroll state ownership (W11-extension motif)**: `internal/tui/components/list.Window` owns `cursor + scroll + itemCount + viewportRows` with `WithItemCount` / `WithViewport` resync. Migrated surfaces include extracted screen-local pickers such as `relationshippicker.Screen`; root no longer carries relationship-picker cursor, scroll, or selected-state fields. `activityCursor` retains its bespoke `-1` sentinel. Architecture tests reject extracted screens that import the root package or reintroduce retired relationship discriminator/render symbols.
- **Registered Home contract screen**: `internal/tui/screens/home.Screen` owns the cross-project card payload, cursor/scroll, loading/error projection, delete-confirm presentation state, resize, footer/help, and reload generation. It emits semantic select/create/edit/prepare-delete/delete actions through `screenhost.Outcome`; `internal/tui/home_controller.go` alone resolves repositories, switches project context, creates notification overlays, constructs backup services, executes `ProjectService.Delete`, drains audit/prune warnings, and reloads the screen. Async reload/delete folds require both the current Home route and exact request generation, so stale worker results cannot overwrite a newer screen state. `internal/arch/tui_screen_boundary_test.go` ratchets the package and keeps `internal/tui/render_home.go` retired.
- **Generic dir-loader with explicit collision policy**: `internal/config/loadfromdir.go`'s `LoadFromDir[T any](dir, opts) ([]T, []SourceWarning, error)` collapses 4 hand-rolled walks (`LoadNotifications`, `LoadLanguages`, `LoadSkills`, `LoadLaws`, `LoadPersonas`, `LoadTemplates`) into one parameterised by `CollisionPolicy` (`CollideError` / `CollideOverwrite` / `CollideKeepFirst`). The policy is declared per-callsite — no verbal contract. Per-domain `MaxFileBytes` stays distinct (`MaxNotificationFileBytes` 100 KB / `MaxLanguagePackBytes` 1 MB / `MaxEntityFileBytes` 10 MB). Optional `OnDecodeError func(path, isCustom, err) (*SourceWarning, recovered bool)` lets the notification loader keep its "skip broken custom files with warning" semantic without polluting other callsites. Multi-suffix support (`Suffixes []string`) handles `.yaml` + `.yml` for notifications and languages.
- **Typed SQLite constraint errors**: `internal/sqlite/sqlutil/constraint.go`'s `MapSQLiteError(err) error` unwraps `modernc.org/sqlite`'s `*sqlite.Error.Code()` (extended SQLite result codes `SQLITE_CONSTRAINT_UNIQUE` / `_FOREIGNKEY` / `_CHECK` / `_NOTNULL` from `modernc.org/sqlite/lib`) into a typed `ConstraintError{Violation, Table, Field, Cause}`. Field extraction parses the trailing `table.column` token from SQLite's message (forgiving — parse failure leaves the wrapper functional). Replaces the previously-brittle `strings.Contains(err.Error(), "UNIQUE constraint failed")` check; `plans.go` uniqueness paths + `tags.go` `AddTaskTag` / `AddProjectTag` FK paths route through it. `AddTaskTag(phantom tag_id)` and `AddProjectTag(phantom tag_id)` previously surfaced as `domain.ErrInternal`; they now return `domain.ErrValidation` with `{"field": "tag_id", "value": <id>}`.
- **SQLite NULL coercion + scan consolidation**: `internal/sqlite/sqlutil/null.go` (`NullStringOr` / `NullInt64Ptr` / `NullTimePtr`) replaces inline `if v.Valid { … }` ladders across `plans` / `tasks` / `errors` / `events` / `activity_logs`. `internal/sqlite/sqlutil/scan.go` (`Scanner` interface, `ScanRow[T]`, `ScanAll[T]` generic closures) consolidates `plans.go`'s previously-divergent `scanPlan` + `scanPlanRows` into a single `decodePlan(scan func(...any) error) (domain.Plan, error)` closure used by 4 `ScanRow` callsites + 1 `ScanAll` callsite. Adding a column to one path now requires updating the same closure — drift is a compile-time impossibility. Other entities (`tasks`, `comments`, `tags`, `projects`, `errors`) keep inline scans; they opt in only if a second helper appears.

- **Explicit search-index maintenance**: `OpenSearchMaintenance` pins the physical `*sql.Conn` whose database inode was verified at open and serializes check, snapshot, and reindex through an internal mutex. Confirmed destructive repair uses the shared exact-generation preparer to read `data_version`, create/verify a candidate backup, re-read `data_version`, acquire `BEGIN IMMEDIATE`, and read it again. Any external commit discards the identity-checked candidate and retries; only a backup matching the locked generation is retained before the in-transaction policy check and rebuild. Reconstructive-only work is detected under `BEGIN IMMEDIATE` and remains backup-free. Reindex failure rolls back evidence; repeated churn aborts after three attempts. A cross-process backup-directory lease spans snapshot, mutation, and identity-safe rooted pruning (`internal/sqlite/exact_generation_recovery.go`, `internal/sqlite/search_integrity.go`, `internal/app/backup_lease.go`, `internal/cli/db.go`).
- **SQLite-consistent backups**: standalone snapshots reject source and destination symlink components, pin the selected source connection/inode, and use parameter-bound `VACUUM INTO` to include committed main/WAL state. Staging is opened through pinned `os.Root`; Unix creates `0700`/`0600` objects, uses descriptor-relative SQLite paths, and fsyncs directories. Windows does not treat POSIX mode bits as ACL guarantees: rooted creation does not install or validate private DACLs, so confidentiality requires deployment-managed private native ACL inheritance. An identity-checked sharing handle denies stage delete/rename through `VACUUM` and verification, file contents are flushed, and unsupported directory-entry crash durability is not claimed. No-force hard-link publication never replaces a name. Force publication retains the previous regular destination under a descriptor-bound private rollback link until cleanup/durability succeeds, restoring the exact prior inode on failure. Parent identities are revalidated and deferred cleanup errors are joined. Production CLI and TUI use Store-bound SQLite writers; generic app tests may retain `AtomicCopyFile` (`internal/sqlite/backup_snapshot*.go`, `internal/app/backup_service.go`, `internal/cli/backup.go`, `internal/cli/tui.go`).
- **Generation-safe project deletion and retention**: `ProjectService` detects the optional atomic repository + backup-lease ports in production while preserving its legacy fake/non-SQLite fallback. Search repair and project deletion share `prepareExactGeneration`, with named policies preserving their different pre-mutation candidate retention decisions. `Store.DeleteProject` and `Store.DeleteProjectWithBackup` retain ownership of their respective transaction lifecycles while both delegate the event-first purge, FK project cascade, and not-found check to the package-private `deleteProjectRows` executor primitive. The backup wrapper commits only after that primitive runs on the prepared pinned transaction, proving all rows deleted under the lock exist in the retained image. `RunLeasedDestructiveOperation` holds `BackupService.WithLease` across snapshot, mutation, and normal/failure pruning, and reports lease-release failures after commit as warnings rather than retryable failures. Prune/discard quarantine candidates with descriptor-relative rename, verify the moved inode, and only then unlink. Rollback is bounded; rollback failure invalidates the physical driver connection before the pool can reuse it (`internal/sqlite/exact_generation_recovery.go`, `internal/app/backup_lease*.go`, `internal/app/project_service.go`, `internal/sqlite/projects.go`).

## Infrastructure

- **GitHub Actions workflows** (`.github/workflows/`):
  - `release.yml` — triggered by `pull_request: closed` against `master`. Release-please creates a draft; GoReleaser v2.17.0 builds but cannot publish; an isolated keyless Cosign v3.1.1 job signs the manifest/checksums and SLSA v1 provenance, verifies the exact GitHub workflow certificate identity, then runs both production strict installers against those fresh bundles through a loopback release server before handing verified files to publication. Every action is commit-pinned and only the signing job receives `id-token: write`.
- **Merge gate**: validation is local-first. `mise run check` runs `test`, `lint`, `vuln`, and `docs:check`; the tracked `scripts/hooks/pre-push` hook invokes the same gate and posts the commit status after the push makes the SHA reachable on GitHub. No `ci.yml` / `ci-docs.yml` workflow is present in the current tree.
- **No Dockerfile / container orchestration**: distribution is via `goreleaser`-built binaries plus `install.sh` / `install.ps1`.
- **Local toolchain**: `.mise.toml` pins Go 1.25.13, GoReleaser 2.17.0, Cosign 3.1.1, `golangci-lint`, and `govulncheck`.
- **Local tasks** (`mise run <task>`): `fmt`, `test`, `build`, `release:dry-run`, `install`, `dev:sync`, `tui`, `lint`, `vuln`, `check`, `install:mcp:claude`, `install:mcp:claude-desktop`, `install:mcp:opencode`, `uninstall`, `purge`.
- **Runtime data**: SQLite at `~/.local/share/omakiten/omakiten.db` (or `$XDG_DATA_HOME` / `$OMAKITEN_HOME/data`); recoverable state such as database backups lives under `~/.local/state/omakiten/backups` (or `$XDG_STATE_HOME` / `$OMAKITEN_HOME/state`).
- **Runtime config**: `~/.config/omakiten/config/<active>.yaml` (basename recorded in `<config-dir>/.active`; `custom/<name>.yaml` shadows same-named root profiles; resolver falls through to discovery when the named profile is missing) plus file-backed assets under sibling folders: markdown entities (`skills/`, `laws/`, `personas/`, `templates/`) and YAML assets (`themes/`, `notifications/`, `languages/`).
