# Contributing

## Commit Standards

- Use [Conventional Commits](https://www.conventionalcommits.org/).
- Write every commit message in English.
- Format: `type(scope): concise summary` or `type: concise summary`.
- Types: `feat`, `fix`, `docs`, `refactor`, `chore`, `test`, `build`, `ci`, `perf`.
- Breaking changes: add `!` after type/scope (e.g., `feat!: remove deprecated API`).

## Branch Naming

- Feature: `feature/{short-name}` (e.g., `feature/audio-badges`)
- Fix: `fix/{short-name}` (e.g., `fix/duplicate-insert`)
- Use lowercase kebab-case. Keep names short and descriptive.

## Project Knowledge Base

When `architecture.md` and `requirements.md` exist in the repository, all planning and implementation work **must** align with the documented patterns, conventions, and constraints. These files are generated by `/document` and represent the verified state of the project.

- Default location: `.docs/`, but they may reside anywhere in the repository.
- Skills that consume these files must search for them before proceeding.

## Workflow Updates

Before starting a new workflow cycle, check if the upstream repository has newer commits:

1. Compare the local workflow version against `https://github.com/This-Is-NPC/assisted_workflow` (use `gh api` or `git ls-remote`).
2. If updates exist, summarize what changed (new skills, modified skills, bug fixes, etc.).
3. Present the summary to the user and ask whether they want to update.
4. If the user confirms, run the appropriate install script with `--update` to apply changes while preserving `CONTRIBUTING.md`.

## Code Standards

### Toolchain

- Go `1.25.x` (toolchain pinned by `.mise.toml` to `1.25.9`).
- `golangci-lint` v2 (config in `.golangci.yml`, linters: `depguard`, `govet`, `ineffassign`, `staticcheck`, `unused`).
- `govulncheck` for vulnerability scanning.
- `gofmt` for formatting.

Use `mise run check` (= `test` + `lint` + `vuln`) before sending a PR. Individual tasks are documented in `.mise.toml`.

### Architecture boundaries (enforced)

The codebase follows hexagonal architecture (`internal/app/doc.go`). Two layers enforce it:

- **`internal/arch/arch_test.go`** — parses every non-test file under `internal/` and fails the build on forbidden cross-package imports.
- **`.golangci.yml` `depguard` rules** — same forbidden edges as lint warnings so editor + CI surface them inline.

Rules in plain English:

- `internal/domain` is the inner core; it imports nothing else from `internal/`.
- `internal/app` talks to adapters via ports declared in `internal/app/ports.go`; it never imports `internal/sqlite`, `internal/configstore`, `internal/tui`, `internal/cli`, `internal/mcp`, `internal/agent`, or `internal/agentruntime`.
- `internal/sqlite` and `internal/configstore` are leaf adapters; they never import each other, `internal/app`, or any consumer adapter.

Run `go test ./internal/arch/...` after structural changes.

### Testing

- Standard library `testing` only.
- Prefer table-driven tests; integration-style tests for CLI/MCP flows are welcome and live alongside the package.
- Coverage target: don't drop below the current baseline (`go test -coverprofile=/tmp/coverage.out ./... && go tool cover -func=/tmp/coverage.out`).

### Documentation

- User-facing guides live under `.docs/<topic>-guide.md` (`cli-guide`, `tui-guide`, `mcp-guide`, `configuration-guide`, `guards-guide`, `theming-guide`, `data-model-guide`).
- Project-level reference (auto-generated by `/document`): `.docs/architecture.md`, `.docs/requirements.md`.
- When changing behavior covered by an existing guide, update the guide in the same PR.

### CHANGELOG

Notable changes go under the `## Unreleased` section in `CHANGELOG.md`. Release tooling is `release-please` (`release-please-config.json`, `.release-please-manifest.json`) — do not edit version headings by hand.
